================================================================================
ROOT CAUSE: RLS POLICY MISMATCH IN SUPABASE
================================================================================

FAILURE: "new row violates row-level security policy for table 'sessions'"

TECHNICAL ANALYSIS:
────────────────────────────────────────────────────────────────────────────

Location: database/schema.sql, line 121-122

Broken Policy:
  CREATE POLICY facilitator_sessions_policy ON sessions
    FOR ALL USING (facilitator_email = auth.email());

Problem:
  - Policy assumes Supabase Auth is used (auth.email() != NULL)
  - Our architecture uses access codes (no Supabase Auth)
  - Facilitator enters email as plain text, not from auth
  - auth.email() returns NULL for unauthenticated user
  - Condition fails: NULL = 'facilitator@university.edu' → FALSE
  - RLS blocks INSERT operation

Architecture Mismatch:
  ┌─────────────────┬──────────────────────┬──────────────────────┐
  │ Aspect          │ Policy Assumes       │ Reality (Our App)    │
  ├─────────────────┼──────────────────────┼──────────────────────┤
  │ User Auth       │ Supabase Auth        │ No auth (access codes)
  │ Facilitator ID  │ auth.email()         │ Plaintext email      │
  │ Access Control  │ Email-based (RLS)    │ Code-based (app)     │
  │ RLS Condition   │ auth.email() exists  │ auth.email() = NULL  │
  │ Result          │ ✓ Allow              │ ✗ BLOCK (RLS error)  │
  └─────────────────┴──────────────────────┴──────────────────────┘

================================================================================
SOLUTION: SQL MIGRATION (NOT CODE CHANGES)
================================================================================

File: database/MIGRATION_FIX_RLS.sql

What It Does:
  1. DROP: facilitator_sessions_policy (auth.email() based)
  2. DROP: team_access_policy (incomplete)
  3. DROP: team_decisions_policy (incomplete)
  4. CREATE: 12 new policies (SELECT, INSERT, UPDATE, DELETE per table)
  5. Result: RLS enabled, permissive, works with access-code model

New Policy Model:
  - Sessions: USING (true) - anyone can read/write (isolated by session_code)
  - Teams: USING (true) - anyone can read/write (isolated by team_code)
  - Decisions: USING (true) - anyone can read/write (isolated by team_id)
